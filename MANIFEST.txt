REQUIRED: APPLY ALL THREE MIGRATIONS, IN ORDER
------------------------------------------------------------
  npx prisma migrate deploy      (production / CI)
  -- or, in local dev --
  npx prisma migrate dev
  npx prisma generate

1. 20260818190900_add_activity_log — creates the new ActivityLog table
   only. Adds nothing to any existing table.
2. 20260818200000_add_project_publish_fields — adds 6 new columns to
   Project (published, order, projectUrl, clientName, seoTitle,
   seoDescription). Backfills published=true for every row where
   status='COMPLETED' — the only data-mutating statement, and it only
   sets the new column.
3. 20260818210000_add_service_approach_and_faq_link — adds `approach` to
   Service, and a nullable `serviceId` to FAQ (every existing FAQ row
   becomes serviceId=NULL, i.e. stays a global FAQ exactly as before).

All three are additive only — no existing column is altered or dropped,
no existing row is deleted. Safe to run against a database with real data.

------------------------------------------------------------
PHASE-BY-PHASE SUMMARY
------------------------------------------------------------

PHASE A — Security Audit
- Removed unauthenticated public POST from /api/projects and /api/blog.
- Deleted 4 dead, unauthenticated files (zero references anywhere).
- Added the missing auth+role check to GET /api/dashboard/settings.
- Fixed a broken Prisma include that made every GET /api/orders/[id] 500.
- Root-caused and fixed "Create Project POST not working": slug was
  required but the dashboard form always sends '', so validation failed
  before the server's slugify() fallback could run (fixed the identical
  latent Blog bug too).

PHASE B — Dashboard Core
- New ActivityLog model + logActivity() helper, instrumented at 7
  mutation points (lead created, offer created/accepted, order created,
  message sent, blog published, project updated, service status changed).
- Replaced the 100%-mocked /dashboard/activity and /dashboard/reports
  pages with real Prisma-backed data.
- Notification bell now polls every 30s + revalidates on focus.
- Added a "View Website" sidebar link; caught and fixed a near-miss that
  would have deleted the sidebar's real, working Logout button.

PHASE C — Projects
- Decoupled publish visibility (new `published` boolean) from the
  existing `status` lifecycle enum — a project could previously never be
  a private draft once COMPLETED, or shown publicly while IN_PROGRESS.
- Added order, projectUrl, clientName, seoTitle, seoDescription.
- Built app/portfolio/[slug]/page.tsx — a public project detail page
  that did not exist before at all.
- Added published projects to the sitemap.

PHASE D — Services
- Added Service.approach ("Our Approach" section) and FAQ.serviceId
  (service-specific FAQs, reusing the existing global FAQ model instead
  of duplicating it).
- Enforced "FIXED_PRICE requires a price" server-side (was client-only —
  a direct API call could bypass it before).
- Wired the homepage FAQ section to real database data — it was 100%
  hardcoded from constants/faq.ts with zero connection to the FAQ
  dashboard; that whole dashboard CRUD page had no visible public effect
  at all until now.
- Added the two sections PRD explicitly asked for on the service detail
  page that were missing entirely: service-specific FAQs and Related
  Services.
- Built a real, database-driven Services mega-menu in the navbar — it
  was previously a hardcoded static link with no dropdown whatsoever.
  Desktop hover/click dropdown (keyboard accessible, closes on outside
  click/Escape), mobile expandable accordion.
